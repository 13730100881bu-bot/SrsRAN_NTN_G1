# AI在通信软件辅助编程中的测评计划

日期：2026-05-07
项目：srsRAN NTN 多波束 / beam hopping 开发样本
测评目标：评估 AI 在通信软件开发中的实际辅助价值、工程边界和落地风险。

## 1. 测评范围

本轮采用“小样本实测 + 可复盘证据”的方式，不做泛泛调研。

样本任务：
- NTN beam hopping table 与 controller
- NTN 配置管理器接入 flexible O-DU
- `ntn_config_update` 远程命令解析
- `ntn_test` 单元测试与 CMake 接入

证据口径：
- 当前目录不是 git 仓库，因此不使用提交历史作为证据。
- 本轮使用文件修改时间、源码范围、构建产物、CTest 日志和人工审查记录作为证据。

## 2. 测评维度

| 维度 | 评价内容 | 评分口径 |
|---|---|---|
| 代码理解 | 是否能快速定位模块职责、调用链、接口边界 | 0-20 |
| 实现辅助 | 是否能产出符合工程风格的实现、校验和集成代码 | 0-20 |
| 测试补齐 | 是否能把协议/边界/时序问题转成可运行测试 | 0-20 |
| 调试验证 | 是否能定位构建环境、复跑目标测试、解释失败/通过结果 | 0-15 |
| 风险识别 | 是否能发现 AI 生成代码容易遗漏的实时性、并发、协议风险 | 0-15 |
| 落地可控性 | 是否能形成 CI、审查、专家复核的工程闭环 | 0-10 |

满分 100 分。

## 3. 实施步骤

1. 样本归档
   - 列出本轮涉及文件、行数、修改时间。
   - 标注远程命令、配置管理、核心算法和测试入口。

2. 构建与单测
   - 在 WSL 构建环境执行：
     - `cmake --build . --target ntn_test -j2`
     - `ctest -R ntn_test --output-on-failure`
   - 记录 target 构建、CTest、gtest 结果。

3. 测试覆盖检查
   - 列出 `ntn_test --gtest_list_tests` 的用例。
   - 对照功能链路确认覆盖项与缺口。

4. 代码质量检查
   - 检查参数边界、类型收窄、断言、线程锁、定时器、生命周期和日志路径。
   - 如果环境具备静态工具，则补跑 `clang-tidy` 或 `cppcheck`；本轮环境未发现这两个工具。

5. 评分与结论
   - 按维度给出评分。
   - 明确 AI 适合承担的任务、必须人工复核的任务和下一轮补测项。

## 4. 通过标准

本轮样本视为“AI辅助开发可行性样本”需满足：
- 目标代码可构建。
- 目标单测通过。
- 有明确测试覆盖说明。
- 至少完成一次代码风险审查。
- 能列出后续进入真实迭代前必须补齐的验证项。

本轮不宣称：
- AI 带来确定百分比效率提升。
- AI 可替代协议专家。
- 单元测试通过即可证明空口/系统场景正确。
